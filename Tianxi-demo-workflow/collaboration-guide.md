# 团队协作说明

这套工作流默认由设计/需求方、实现者、评审方共同使用。设计团队不需要写代码，但需要提供清晰的目标、资产、优先级和批注。

## 启动前设计/需求方需要提供

- Demo 的一句话目标：这次演示要让别人相信什么。
- 核心场景：用户是谁、从哪里进入、要完成什么任务。
- 主流程清单：按演示顺序列出必须跑通的步骤。
- 页面优先级：哪些页面必须高还原，哪些页面只需风格一致。
- Figma 链接：标注关键 frame、node、组件状态。
- 资产包：头像、icon、运营位图、插图、SVG、PNG。
- 文案和示例数据：角色名、卡片标题、描述、按钮文案、toast 文案。

## P0 阶段怎么配合

设计方重点确认：

- 入口是否正确。
- 主流程是否能走通。
- 页面名称、导航、核心数据是否方向正确。
- 是否遗漏关键页面或关键按钮。

不要在 P0 纠结：

- 1-2 px 的间距。
- 复杂 hover 状态。
- 非关键页面视觉细节。
- 低频边缘状态。

## P1 阶段怎么配合

设计方重点标注：

- 关键页面：需要高还原的页面或区域。
- 关键组件：输入框、弹窗、卡片、tab、列表、toast。
- 关键状态：选中、hover、disabled、loading、empty。
- 关键资产：头像、icon、SVG、图片替换关系。

批注要尽量具体：

- 指向具体元素。
- 说明当前问题。
- 说明期望结果。
- 如果有设计稿或截图，附上链接或文件名。

## P2 阶段怎么配合

设计方重点验收：

- 演示路径是否自然。
- 关键页面是否足够像设计稿。
- 是否还有明显穿帮、错位、乱码、文案不一致。
- 现场演示是否需要固定默认页面或默认状态。

## 评审方怎么配合

- 用统一的线上链接评审，不要多人看不同版本。
- 一轮反馈尽量一次性集中给出。
- 每条反馈说明优先级：必须改、建议改、可延后。
- 不把新需求混入 bug 批注；新流程单独开下一轮。

## 实现者职责

- 先保证流程可演示。
- 把内容尽量数据化，方便替换。
- 维护资产目录和版本号。
- 每轮提交前自测关键路径。
- 每轮交付说明改了什么、没改什么、哪里需要继续确认。
